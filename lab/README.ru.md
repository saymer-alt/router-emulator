# Keenetic CI Lab — автоматическая лаборатория маршрутизаторов

Первая реализация на основе исходного [Router Emulator](https://github.com/stavultras/router-emulator).
Задача — убрать повторяющиеся ручные 30-минутные циклы: сценарий запускает виртуальную
плату, ждёт события UART, проверяет HTTP через `127.0.0.1`, выполняет перезагрузку и
пишет `report.json` + `junit.xml`. Само по себе появление файла пресета НЕ
доказывает работу конкретной прошивки.

## Два независимых пути

| Путь | Состояние | Что доказывает |
|---|---|---|
| **MT7981 / Cudy WR3000P / OpenWrt** | Автоматическая CI-проверка в `.github/workflows/keenetic-lab.yml` | Загрузка QEMU, WAN offline, LuCI, эмулированный reset и повторная доступность |
| **MT7621 / Xiaomi Mi Router 3G / Keenetic Ported** | **Эксперимент, нужен локальный образ и фактический лог** | Наличие UART-маркеров портированной системы до и после reset; **ещё не** поддержка/прохождение KAS |
| **KN-1012 / оригинальная KeeneticOS** | Пока нет подтверждённого E2E | Аппаратный пресет существует, но оригинальная система и Entware не проверены |

Ветка Keenetic Ported **не заблокирована** ожиданием оригинального KN-1012:
есть пресеты `xiaomi-mi-router-3g-uboot` и `xiaomi-mi-router-3g-breed`, а
проект [Router Ported](https://keeneticported.dev/wiki/) выпускает портированные
прошивки для Xiaomi. Но образ должен соответствовать именно **аппаратной модели,
загрузчику и раскладке разделов**, иначе лабораторный запуск ничего не скажет.
Заранее проверять формат образа — обязательно. Нельзя загружать произвольный
firmware.bin как полный дамп NAND без корректной подготовки.

## Автоматическая OpenWrt-проверка

На GitHub: Actions → **Keenetic lab - isolated QEMU regression**.
При изменении `lab/**` в PR тест запускается самостоятельно; доступны
отдельные быстрые unit-тесты и тяжёлый запуск на QEMU.

Для самостоятельного запуска на Linux x86_64 с подготовленным upstream
`Router-Emulator` и его флеш-папкой (`tools/prepare-nand.sh`):

```bash
python3 lab/run.py \
  --emulator-root . \
  --scenario lab/scenarios/openwrt-mt7981.json \
  --preset cudy-wr3000p-v1 \
  --nand-dir ./nand-wr3000p \
  --output-dir ./work/lab-reports/openwrt \
  --max-seconds 1500
```

Здесь `emulator.sh`, `qemu/`, `presets/` и `nand-wr3000p` должны
находиться в рабочем каталоге. Содержимое flash копируется в отдельную
временную директорию; исходный образ **не изменяется**. На каждый запуск
использовать новый пустой каталог отчётов. WAN = `offline`, LAN = `user`
(только loopback). Ни мост к физической сети, ни домашняя маршрутизация,
ни роутеры или VPS не используются.

## Keenetic Ported — следующий реальный эксперимент

После локальной подготовки **правильных разделов** под
`xiaomi-mi-router-3g-uboot` / `xiaomi-mi-router-3g-breed`:

```bash
python3 lab/run.py \
  --emulator-root . \
  --scenario lab/scenarios/keenetic-ported-mt7621.template.json \
  --preset xiaomi-mi-router-3g-uboot \
  --nand-dir /PRIVATE/ported-r3g-flash \
  --output-dir ./work/lab-reports/ported-r3g-$(date +%s) \
  --max-seconds 1500
```

**Это шаблон исследовательского прогона, а не утверждение, что Ported уже загрузился.**
У портированной системы и загрузчика фактические строки UART могут отличаться;
сначала записать их из реального лога и только затем уточнить regex в отдельном
сценарии. Любое несовпадение — FAIL или BLOCKED, не принудительный PASS.
Критерий для следующих этапов: подтверждённые версии `KeeneticOS`,
доступность `ndmc`, `opkg`, корректное `/opt`, среда Entware,
аппаратное соответствие, изоляция сети и восстановление после reboot.

**Не публиковать** файлы портированных или оригинальных прошивок,
дампы NAND, EEPROM/eFuse, ключи, конфигурации, приватные serial-логи,
токены, пароли или snapshots с персональными данными. GitHub hosted runners
запускают **только официальные публичные образы OpenWrt**; для Ported
использовать личный изолированный компьютер/runner, проверить происхождение
образа, условия распространения и убрать секреты из отчётов.

## Формат сценария

JSON в `lab/scenarios/` — массив шагов:
`wait_serial` (Python regex по UART-логу), `send_serial` (одна команда),
`probe_http` (разрешён **только** http://127.0.0.1, без редиректов/proxy),
`reset` (HMP `system_reset`), `sleep`.
У каждого ожидания свой timeout; общий лимит задаётся `--max-seconds`.
После reset прошлый UART-лог **не может** засчитаться как новая загрузка.

`evidence` фиксируется в результате:
`OPENWRT_QEMU_SMOKE`,
`KEENETIC_PORTED_EXPERIMENTAL`,
`KEENETICOS_VIRTUAL`. Даже `PASS` не повышает степень доказательности
автоматически и не разрешает релиз KAS/KNVR/KeenWhite.

## Последующие задачи

1. Убедиться, что сценарий OpenWrt успешно дошёл до **второй** проверки HTTP
после reset, и сохранить конкретный Actions run.
2. Завести у локального испытателя корректный и проверенный образ
Keenetic Ported MT7621, подтвердить загрузчик, UART, `ndmc` и Entware.
3. На подтверждённой виртуальной KeeneticOS добавить реальные сценарии
KAS: clean install → Doctor → повтор → reboot → Doctor → rollback → uninstall.
4. Отдельно перенести сценарии KeenWhite/WDTT и KNVR; жёстко разделять
результаты QEMU и испытания на физическом железе.
5. Синхронизировать upstream QEMU без автоматического слияния, сохраняя GPL-2.0,
авторство и исходный код.

Ранние результаты — экспериментальные. Промышленную сеть, `stable` и
аппаратные устройства они не затрагивают.
