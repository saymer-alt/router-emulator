Separation of the two reset events (the acceptance core)
--------------------------------------------------------
- Event 1, NATIVE reboot: the only "reboot: Restarting system" line in the whole
  log is at console line 1759 (init: SIGKILL -> requesting system reboot ->
  Machine restart), between boot 1 and boot 2.  Boot 2 then re-attached Entware
  from saved config: "disk is set to: KASOPT:/" + "configured init script:
  /opt/etc/init.d/rc.unslung" + "system ready, core startup time is 111 seconds".
- Event 2, QEMU monitor reset: scenario step 37 is action "reset"; lab/run.py
  records the console EOF offset BEFORE sending "system_reset" via the QEMU
  monitor, then sends it.  Boot 3 (console line 3189) follows the breed
  "Booting image from flash bank 0" block with NO init-shutdown lines and NO
  "reboot: Restarting system" line anywhere between boot 2 and boot 3.  Boot 3
  re-attached Entware from saved config the same way ("KASOPT:/" + rc.unslung +
  "system ready, core startup time is 110 seconds").
- The native reboot and the QEMU reset are therefore two separate, individually
  observable events in the guest log, exactly as the task requires.

MIPSEL_PERSISTENCE derivation
-----------------------------
python3 lab/mt7621/mt7621_gates.py --persistence-scenario
lab/scenarios/ported-mt7621-entware-persistence.json --persistence-report
<real report.json> derives:
  MIPSEL_PERSISTENCE = PASS
  (native_reboot_then_qemu_reset_opt_config_persisted)
The gate evaluator requires >=3 "system ready" waits, exactly one native reboot
wait, exactly one reset action, one persistence write, two persistence reads, one
sync, >=2 mounts/arch/elf checks, >=2 marker reads, strictly increasing ordering
(write -> native reboot -> boot 2 -> read -> sync -> reset -> boot 3 -> checks),
and report outcome PASS.  No manual gate override was used.

rc.unslung autostart: explicitly NOT_TESTED
-------------------------------------------
The log shows ndm confirming "configured init script: /opt/etc/init.d/rc.unslung"
once per boot (lines 1391, 2944, 4342).  That is the SETTING being applied by the
system, not a measurement of a service actually started by rc.unslung: no scenario
step observes a live Entware process after boot 2 or boot 3 (no service liveness
probe exists in the 47 steps; bash/opkg checks prove package and data persistence,
not autostart).  Per the task, actual rc.unslung service autostart remains
NOT_TESTED; a future cycle would need a persistent init script writing a boot
marker (or a live service probe) right after "system ready" to measure it.
