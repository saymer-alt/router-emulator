# Экономия токенов и GitHub Actions — Router Emulator

Область: изолированная лаборатория QEMU/Ported/Entware. Эти правила дополняют [AGENTS.md](../AGENTS.md), [KAS agent-token-efficiency](https://github.com/saymer-alt/keenetic-auto-setup/blob/main/docs/agent-token-efficiency.md) и Proof Before Build. Они не разрешают обходить безопасность, skip обязательной приёмки или менять физические роутеры.

## Один проверяемый рабочий цикл

1. Зафиксировать `Issue | PR | base/head full SHA | firmware image / version | stage | known PASS / FAIL / BLOCKED / NOT_TESTED | гипотеза | критерий STOP`. Проверить уже завершённые jobs и чужие активные PR до внесения кода. Не запускать двух агентов на одну проблему.
2. Читать сначала точный упавший шаг и несколько строк *санитизированных* маркеров, затем затронутые файлы и тесты. Перед изменением safety-critical `lab/guest.py`, гостевого транспорта, установки Entware/opkg, NAND, setup/teardown, rollback или security gates прочитать изменяемый файл и контракты **целиком на точном SHA**. После правки проверить весь diff.
3. Выполнить дешёвый тест Python/syntax/unit и проверку pins/хешей, потом только обоснованный нативный QEMU gate. Не подменять реальный `opkg` mock-тестом и не выдавать успешное чтение CLI за установку KAS.
4. **Два одинаковых FAIL** с прежним SHA, аргументами и наблюдениями — STOP; открыть новую гипотезу или признать `BLOCKED`. Перезапуск оправдан только новым доказательством transient-проблемы или изменившимся кодом/средой. Не повторять уже зелёные gate без новой причины.
5. Сохранять краткий handoff: `PR | full SHA | gate/status | Actions run / job | категориальный отказ | что не проверено | следующий разрешённый шаг`.

## Как не тратить QEMU-время на GitHub

- Для `lab/**` исходников текущие pull-request workflows могут автоматически запустить **три** ресурсоёмких проверки: OpenWrt/QEMU, Ported/KAS и KNVR. Перед каждым push смотреть фильтры `on.pull_request.paths`, а не запускать такой же workflow ещё раз вручную.
- Изменения только `lab/**/*.md` исключены из этих трёх тяжёлых PR-trigger путей (см. merged #100). Код или смешанный diff не исключены. Изменения самих workflow закономерно запускают проверку их конфигурации.
- В Ported/KAS reusable workflow группа `concurrency` разделяет **caller, ref и stage** (merged #101). Это предотвращает перекрытие разных вызывающих workflows по одному лишь ref; не считать данный YAML-довод полноценным многопоточным live-test без фактических jobs.
- Перед тяжёлым прогоном проверить, что старый PASS совпадает по **точному commit SHA, образу, пакетному lock, stage и профилю**. Для иного входа старый PASS — лишь исторический ориентир.
- `HOST PASS`, `QEMU GUEST PASS`, `FIELD NOT_TESTED` строго разные статусы. Например, MT7621 Entware может быть PASS, но KAS MIPSel остаётся `BLOCKED` без `ext-utils` (#89). Не ослаблять guard для зелёной отчётности.
- Публиковать только заранее разрешённые категории, счётчики и JSON/JUnit; прошивки/NAND, приватный UART/SSH, секреты и адреса остаются вне публичных артефактов. Успешный mock/host gate не подтверждает физический USB-loss, Wi-Fi, ISP или реальный Keenetic reboot.

## Эскалация и границы

Не корректировать production KAS/TeleMT из этого репозитория. Реальные роутеры/VPS, релиз или платный эксперимент требуют отдельного решения владельца. Любой долгий QEMU-цикл должен иметь проверяемый выход и точку остановки, а не бесконечную очередь заданий.

Операционный принцип: **перепроверяем только изменившееся, не переименовываем FAIL/BLOCKED в PASS**.
